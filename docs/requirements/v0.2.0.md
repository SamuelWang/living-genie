# Requirements — v0.2.0

## Overview

Building on v0.1.0's diary CRUD, v0.2.0 adds Living Genie's first AI capability: a
retrieval-augmented chatbot that answers questions grounded in the user's own diary entries. Per
[../roadmap.md](../roadmap.md), this covers the asynchronous chunking/embedding pipeline, a
vector store for embeddings, the RAG retrieval workflow over diary content, and a single chat
interface for talking with that data. The chatbot, displayed in the UI as **"Genie"**, is designed
as the first of what will eventually be multiple data sources (diary now, others later), but only
diary entries are wired in for v0.2.0.

For the technical design supporting these requirements, see [../architecture.md](../architecture.md).

## Goals

- Automatically index diary entries (chunk + embed) in the background as they're created or
  edited, without blocking the save flow.
- Store embeddings in a vector store, scoped per user.
- Retrieve relevant diary excerpts at query time and use them to ground chatbot answers (RAG).
- Provide one chat interface where the user can ask questions about their diary and get a
  grounded, cited answer.
- Persist conversations so a user can revisit or continue a previous chat.
- Keep the chatbot scoped to the user's own diary data and to help with using Living Genie
  itself, rejecting requests outside that scope rather than acting as a general-purpose assistant.

## Non-goals / Out of scope

The following are explicitly **not** part of v0.2.0:

- Any data source other than diary entries — "future data sources" is a design consideration for
  extensibility, not something implemented this phase.
- A guarantee that a just-saved entry is immediately reflected in chat answers — indexing is
  asynchronous, so there's a short, unspecified lag.
- Editing or regenerating a past assistant message.
- Exporting or sharing a conversation.
- Multi-modal understanding — the chatbot reads diary text; it does not analyze embedded images.
- Any change to diary CRUD or authentication themselves.
- Model fine-tuning/training — inference against pre-trained local models only.
- Acting as a general-purpose assistant for topics unrelated to the user's own diary data or to
  using Living Genie itself (e.g. general knowledge questions, unrelated task requests) — these
  are rejected, not answered (see Functional requirement 8).

## Users

Same as v0.1.0: each authenticated account's conversations and retrieval are scoped strictly to
that account's own diary entries — one account can never see or retrieve another's data via chat.

## Functional requirements

### 1. Diary entries are indexed automatically

As the user, when I create or edit a diary entry, its content is chunked and embedded in the
background, without blocking or slowing down the save action.

**Acceptance criteria**
- Saving an entry returns immediately; indexing happens asynchronously afterward.
- If the app restarts before indexing finishes, indexing resumes/completes without user action.
- Editing an entry re-indexes its new content; retrieval no longer surfaces the stale version.

### 2. Deleting an entry removes it from retrieval

As the user, once I delete a diary entry, the chatbot can no longer reference it.

**Acceptance criteria**
- After deletion, the entry's content is excluded from future retrieval and removed from the
  vector store.

### 3. Start a new conversation

As the user, I can start a new chat conversation and ask a question about my diary.

**Acceptance criteria**
- The chatbot answers using relevant excerpts retrieved from my own diary entries when available.
- If no relevant diary content exists (empty diary, or nothing relevant to the question), the
  chatbot says so rather than fabricating an answer.
- The chatbot's answer indicates which diary entries it drew from, so the user can find the source.

### 4. Continue a previous conversation

As the user, I can reopen a past conversation and keep asking questions with that conversation's
prior messages as context.

**Acceptance criteria**
- New messages in a reopened conversation can reference earlier turns in the same conversation.
- Only the owning account can reopen/continue its own conversations.

### 5. View my conversations

As the user, I can see a list of my past conversations, ordered by most recent activity, and open
any of them.

**Acceptance criteria**
- The list only ever includes the authenticated account's own conversations.

### 6. Delete a conversation

As the user, I can delete a conversation, with a confirmation step to prevent accidental loss.

**Acceptance criteria**
- Once confirmed, the conversation and its messages are removed and no longer listed.
- Only the owning account can delete it; another account's delete attempt behaves identically to
  deleting a nonexistent conversation.

### 7. Chat responds in the conversation's language

As the user, I can converse in Traditional Chinese or English (matching v0.1.0's supported UI
languages), and the chatbot's replies come back in that same language.

**Acceptance criteria**
- A question asked in Traditional Chinese gets a Traditional Chinese reply, and likewise for
  English; this is independent of the diary entries' own language, which is never translated.

### 8. Chatbot stays scoped to diary data and app help

As the user, if I ask the chatbot something unrelated to my diary entries or to how Living Genie
works, it declines to answer rather than acting as a general-purpose assistant.

**Acceptance criteria**
- Questions grounded in retrieved diary content, and questions about how to use Living Genie
  itself (its features, supported languages, etc.), are answered normally.
- Any other request (general knowledge, unrelated tasks, role-play, etc.) gets a clear rejection
  message instead of an attempted answer.
- This is a firm scope boundary, not a soft suggestion — rejection applies regardless of how the
  request is phrased.

## Data requirements

Each indexed chunk conceptually needs: a reference to its source diary entry, the owning user, the
chunk's text/position within the entry, and its embedding vector.

Each conversation has: an id, the owning user, and created/last-active timestamps.

Each message has: an id, its conversation, a role (user or assistant), its text content, a
created-at timestamp, and — for assistant messages — the diary entries it cited, if any.

## Non-functional requirements

- The full stack, including the new indexing pipeline, vector store, and local LLM inference,
  still runs locally via `docker compose up`, alongside the v0.1.0 services.
- Indexing and chat inference use locally-hosted models sized to run on typical consumer hardware
  without requiring a dedicated GPU.
- No specific latency/throughput target (small-scale local deployment, as in v0.1.0 — not
  designed for concurrent load at internet scale), but the chat UI must show clear in-progress
  feedback (e.g. streaming text or a loading indicator) rather than appearing frozen during
  generation.
- Both frontend and backend must have unit/integration tests covering: indexing triggers on
  save/edit/delete, retrieval scoping (no cross-user leakage), and conversation CRUD. No specific
  coverage percentage is required for v0.2.0.

## Acceptance criteria for v0.2.0 completion

- Running `docker compose up` brings up the full stack including the new indexing, vector store,
  and inference infrastructure.
- Creating or editing a diary entry results in it becoming retrievable by the chatbot once
  background indexing completes.
- Through the UI, the user can start a conversation, ask a question, and receive an answer
  grounded in their own diary entries with source references.
- Through the UI, the user can list, reopen, continue, and delete their conversations.
