# Requirements — v0.6.0

## Overview

Building on v0.1.0–v0.5.0, v0.6.0 opens Genie up to more than one model. Today every AI call
goes straight through the `ollama` Python client against one hard-coded chat model
(`OLLAMA_CHAT_MODEL`) and one embedding model (`OLLAMA_EMBEDDING_MODEL`): `embeddings.py` wraps
the client, `chat.py` hand-rolls the tool-calling loop and a separate structured-output
"did the user confirm?" classifier, `todo_tools.py` defines tools as raw JSON-schema dicts, and
`docker-compose.yaml` makes the `ollama` service a hard dependency of `web-api` and `worker`. That
means the app can only run where a local model can run, Genie's quality is capped by what fits
on the host GPU, and swapping providers would mean rewriting the AI layer.

v0.6.0 moves the AI layer onto open-source **LangChain** as the common abstraction over chat
models, tool calling, streaming, and embeddings, and uses it to offer cloud models from
**Anthropic**, **OpenAI**, and **Google Gemini** alongside local **Ollama** models. Every chat
model is individually enabled through environment settings, and the user picks one of the enabled
models per conversation in the chat UI. At the same time, Genie's todo actions are simplified to
plain LangChain tool calling, dropping the bespoke stored-pending-action confirmation flow in
favor of real multi-turn history, and Ollama moves into its own Compose file so it only runs when
local models are actually in use.

Because Living Genie holds personal diary data, sending that data to a cloud provider is a
deliberate, visible choice in this version — never a silent default.

For the technical design supporting these requirements, see [../architecture.md](../architecture.md).

## Goals

- Replace direct `ollama` client usage with open-source LangChain (`langchain`, `langchain-core`,
  and the `langchain-ollama`, `langchain-anthropic`, `langchain-openai`, `langchain-google-genai`
  integrations) wherever LangChain covers the feature: chat models, tool definition and binding,
  the tool-calling agent loop, message types, streaming, and embeddings.
- Simplify Genie's agent to pure LangChain tool calling: todo tools defined with `@tool`
  (Pydantic argument schemas) and run by LangChain's agent loop with its built-in iteration
  limit. Drop the bespoke confirmation machinery — the `conversations.pending_action` column, the
  separate `pending_action_is_confirmed()` classifier call, `pending_action_reply()`, the router's
  "execute the stored action on yes" short-circuit, and the deterministic-failure-reply special
  case.
- Keep app-owned logic LangChain doesn't replace: chunking, the todo database operations behind
  each tool, and per-account data scoping.
- Drop the Qdrant hybrid recency re-ranking. Retrieval relies on vector similarity alone, and
  every embedded chunk carries its source's full context, including the diary date, so the
  vector itself holds that information.
- Let the self-hoster enable or disable each chat model individually through environment
  settings, across four providers: Ollama (local), Anthropic, OpenAI, Google Gemini.
- Let the user choose any enabled model per conversation in the chat UI, and switch it
  mid-conversation.
- Make the embedding provider and model a single, system-wide, environment-configured choice
  (Ollama or a cloud provider), with a documented re-index path when it changes.
- Make it obvious when a model sends data off the host.
- Run Ollama from its own Compose file so the stack runs without it when only cloud models are
  enabled.
- Preserve v0.5.0's observability (spans, metrics, logs) across every provider.
- Update all current-state documentation to describe the multi-provider setup.

## Non-goals / Out of scope

The following are explicitly **not** part of v0.6.0:

- LangSmith, LangGraph Platform, or any hosted LangChain service — open-source packages only.
- Agent frameworks or multi-agent orchestration beyond the single tool-calling agent Genie needs.
- Per-user API keys / bring-your-own-key — provider keys are configured once by the self-hoster.
- An admin UI for enabling or disabling models — environment settings only.
- Per-user or per-account model allow-lists — every account sees the same enabled models.
- User-selectable embedding models, or automatic re-indexing when the embedding configuration
  changes — re-indexing is a documented manual step.
- Providers other than Ollama, Anthropic, OpenAI, and Google Gemini.
- Cost tracking, usage quotas, or spend dashboards.
- Automatic fallback/failover between providers when one is unavailable.
- Multimodal input (sending diary images to a model).
- Any replacement retrieval-ranking step: no keyword/BM25 hybrid search, no re-ranker model, and
  no date-range filtering parsed from the question.
- A confirm/cancel button UI for todo actions — confirmation stays conversational, as in v0.3.0.

## Users

This version has two audiences:

- **The end user** chatting with Genie, who can now pick which enabled model answers in each
  conversation and can see whether that model is local or cloud.
- **The self-hoster** (today the same person), who decides which providers and models are
  enabled, supplies API keys, chooses the embedding provider, and decides whether to run Ollama.

Data scoping is unchanged: each account's diary entries, todos, conversations, and retrieval are
strictly its own, whichever model is in use.

## Functional requirements

### 1. Configure which chat models are available

As the self-hoster, I can enable or disable each provider and each chat model through
environment settings, without code changes.

**Acceptance criteria**
- Each provider has its own enable switch (e.g. `OLLAMA_ENABLED`, `ANTHROPIC_ENABLED`,
  `OPENAI_ENABLED`, `GOOGLE_ENABLED`) and its connection setting (`OLLAMA_URL`,
  `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GOOGLE_API_KEY`).
- Each provider has its own list of enabled chat model ids (e.g. `OPENAI_CHAT_MODELS`), so every
  model has its own switch: a model is offered only if its provider is enabled and it is listed.
- `DEFAULT_CHAT_MODEL` names the model used for new conversations and must refer to an enabled
  model.
- Startup fails fast with a clear error if an enabled provider is missing its API key/URL, if no
  chat model is enabled at all, or if the default model isn't enabled.
- A disabled provider's SDK client is never constructed and its API is never called.

### 2. See and pick an enabled model in the chat UI

As the user, I can see the models available to me and choose one for the conversation I'm in.

**Acceptance criteria**
- An authenticated `GET /models` endpoint returns the enabled chat models: a stable id
  (`provider:model`), a display label, the provider, and whether it is local or cloud.
- The Genie chat UI shows a model selector listing exactly those models, translated in zh-Hant
  and en like the rest of the UI.
- New conversations start on `DEFAULT_CHAT_MODEL`.

### 3. Keep the chosen model per conversation, and switch it

As the user, the model I pick sticks to the conversation, and I can change it at any point.

**Acceptance criteria**
- The selected model is stored on the conversation; reopening the conversation restores it.
- Changing the model mid-conversation applies from the next message onward; earlier messages
  are untouched.
- If a conversation's stored model has since been disabled, the UI says so and the next message
  uses the default model; the server rejects unknown or disabled model ids with a 4xx error.

### 4. Every enabled model supports the full Genie feature set

As the user, Genie works the same whichever enabled model I choose.

**Acceptance criteria**
- With any enabled model, Genie answers diary/todo questions from retrieved excerpts, streams its
  reply, and can create, update, complete, and delete todos through LangChain tool calling.
- `create_todo` runs without confirmation. For `update_todo`, `complete_todo`, and
  `delete_todo`, Genie asks the user to confirm in conversation and only calls the tool with
  `user_confirmed=true` after the user agrees; the tool itself still refuses when
  `user_confirmed` is false. There is no stored pending action and no separate confirmation
  classifier call.
- Tool results, including failures, are passed back to the model as tool messages; the number of
  agent iterations per turn is capped by a configurable limit.
- Todos created or changed in a turn are still surfaced as references in the reply, as in v0.3.0.
- Provider-specific generation options (temperatures, Ollama `repeat_penalty`, thinking on/off)
  are configured per provider; options a provider doesn't support are ignored, not errors.

### 5. Record which model answered

As the user, I can see which model produced each Genie reply.

**Acceptance criteria**
- Each assistant message stores the provider and model that produced it.
- The chat UI shows it subtly on each reply.

### 6. Configure the embedding provider system-wide

As the self-hoster, I can choose which provider and model embed diary entries and todos.

**Acceptance criteria**
- `EMBEDDING_PROVIDER` (Ollama, OpenAI, or Google Gemini), `EMBEDDING_MODEL`, and the vector
  size are environment-configured and used through LangChain's `Embeddings` interface for both
  indexing (worker) and query embedding (chat).
- Query/passage prompt prefixes are preserved for models that need them (e.g.
  `embeddinggemma`).
- The Qdrant collection's vector size comes from configuration rather than a hard-coded 768; a
  mismatch with an existing collection is detected at startup with a clear error.
- A documented re-index command re-embeds all diary entries and todos after the embedding
  configuration changes.
- End users never choose the embedding model.

### 7. Retrieve by embeddings alone, with all context in the vector

As the user, Genie finds the right diary entries and todos — including for date-based questions
like "what did I do last weekend?" or "最近一次看醫生是什麼時候?" — because each embedded chunk
carries its full context, not because of a separate re-ranking step.

**Acceptance criteria**
- The Qdrant hybrid recency re-ranking is removed: no recency bonus, no half-life decay, and no
  oversized candidate pool. Retrieval returns the top `RETRIEVAL_TOP_K` chunks by vector
  similarity, still filtered to the current account.
- The `RETRIEVAL_RECENCY_WEIGHT`, `RETRIEVAL_RECENCY_HALF_LIFE_DAYS`, and
  `RETRIEVAL_CANDIDATE_POOL_SIZE` settings are removed.
- Every chunk's embedded text includes all of its source's descriptive information, not just the
  body text:
  - **Diary entry:** the entry date (ISO date plus weekday), the title, and the chunk's content.
  - **Todo:** the title, description, status (pending/completed), due date if set, and creation
    date.
- That information is repeated on every chunk of a multi-chunk source, not only the first, so
  each chunk is self-describing.
- Chunk size limits account for the added information, so a chunk with its metadata still fits
  the configured chunk size.
- Recency questions ("latest", "most recent", "最近", "上次") are answered by the model reading
  the dates in the retrieved excerpts, guided by the system prompt — not by a scoring formula.
- Existing vectors are rebuilt with the new chunk format on upgrade, using the re-index command
  from requirement 6.

### 8. Run the stack with or without Ollama

As the self-hoster, Ollama only runs when I've enabled local models.

**Acceptance criteria**
- `ollama` and `ollama-init` live in a separate `docker-compose.ollama.yaml`; `ollama-init`
  pulls the enabled Ollama chat models and, if Ollama is the embedding provider, the embedding
  model.
- `docker-compose.yaml` and `docker-compose.dev.yaml` contain no Ollama service and no
  `depends_on` on it; with only cloud providers enabled, `docker compose up` runs the full stack
  without an Ollama container.
- `docker-compose.ollama.yaml` works on a host without an NVIDIA GPU; the GPU reservation moves to
  an optional `docker-compose.ollama.gpu.yaml` override.
- The README documents combining the files with `-f` or `COMPOSE_FILE`.
- `/health` and service dependencies don't reference Ollama when it isn't part of the stack.

### 9. Handle provider errors gracefully

As the user, if a cloud provider fails, I get a clear message rather than a broken chat.

**Acceptance criteria**
- Authentication, rate-limit, timeout, and other provider errors surface as the existing SSE
  `error` event with a user-friendly message.
- Timeout, max retries, and max output tokens are configurable per provider.
- Errors are logged with the provider and model, but never with prompt content, diary text, or
  API keys.

### 10. Know when data leaves the host

As the user, I can tell which models send my data off my machine, and I'm told before it first
happens.

**Acceptance criteria**
- The model selector marks each model as local or cloud.
- The first time a user selects a cloud model, they see a one-time notice that diary excerpts,
  todos, and recent conversation will be sent to that provider; the acknowledgement is stored on
  the account.
- The documentation states plainly that a cloud embedding provider sends all diary and todo
  content to that provider at indexing time.
- Only open-source LangChain packages are used; no LangSmith account, API key, or hosted
  LangChain service is required or configured. (`langchain-core` installs the `langsmith` client
  library as a dependency, but it sends nothing unless `LANGSMITH_TRACING` /
  `LANGCHAIN_TRACING_V2` and an API key are set.) The app sets no LangSmith variables and the
  `.env.example` files don't mention them, so no telemetry leaves the host by default — the
  v0.5.0 rule is kept.

### 11. Genie remembers the real conversation, including its own actions

As the user, when I reply "yes" to Genie's proposed change, Genie knows what it proposed and
what it has already done.

**Acceptance criteria**
- Conversation history is sent to the model as LangChain messages (human, AI with tool calls,
  tool results), not flattened into a single text block.
- Tool calls and their results are persisted with each assistant turn, so later turns see which
  tools actually ran and what Genie proposed.
- Retrieved diary/todo excerpts are added for the current turn only; history depth stays
  configurable (`CHAT_CONTEXT_TURNS`).

### 12. Check that each model behaves as an agent

As the self-hoster, I can check that a model handles Genie's todo flows correctly before I
enable it.

**Acceptance criteria**
- A scripted scenario suite can run against any enabled model and reports pass/fail per model.
  It covers: creating a todo; propose → confirm → update/complete/delete; the user declining;
  a duplicate title that needs a due date to tell apart; a question with and without matching
  excerpts; an off-topic request being refused; and both zh-Hant and en.
- The default local model passes the suite before release, and the results are recorded in the
  v0.6.0 release notes.
- Startup rejects, with a clear error, any configured chat model that can't bind tools.

### 13. Replies stream cleanly from every provider

As the user, I only ever see Genie's answer, never its internal reasoning.

**Acceptance criteria**
- Reasoning/thinking output (Anthropic thinking blocks, Gemini thoughts, Ollama `think`) never
  reaches the SSE token stream or the stored message content.
- Provider-specific content-block formats are normalized to plain text tokens before streaming.

### 14. Observability keeps working across providers

As the self-hoster, my v0.5.0 traces, metrics, and dashboards still work whichever provider
answered.

**Acceptance criteria**
- The existing chat spans (`chat.embed_query`, `chat.qdrant_search`, `chat.build_prompt`, each
  model call, each `chat.tool_call`) and worker spans (`job.chunk`, `job.embed_chunks`,
  `job.qdrant_upsert`) remain.
- Model-call spans and metrics carry `llm.provider` and `llm.model` attributes/labels.
- The v0.5.0 Grafana dashboards keep working.

### 15. Documentation describes the multi-provider setup

As the self-hoster, the documentation matches how v0.6.0 actually works.

**Acceptance criteria**
- Every current-state document that assumes a local-Ollama-only system is updated: root
  `README.md`, `web-api/README.md`, `web/README.md`, `docs/architecture.md` (AI layer,
  LangChain, model registry, embedding configuration, removal of the pending-action flow,
  Compose layout), `CLAUDE.md` where affected, `.env.example` and `web-api/.env.example` (every
  provider switch, key, and model list), and `docs/ollama-model-evaluation.md` (reframed as
  guidance for choosing local models).
- Historical per-version documents (`docs/requirements`, `docs/execution`, and
  `docs/release-notes` for v0.1.0–v0.5.0, and past `CHANGELOG.md` entries) stay unchanged as
  records; v0.6.0 gets its own release notes and `CHANGELOG.md` entry.

## Data requirements

- **Conversations** gain the selected chat model (`provider:model`, nullable; null means the
  default model) and lose the `pending_action` column.
- **Messages** gain the model that produced each assistant message (nullable; null for messages
  from before v0.6.0) and the tool calls and tool results made during that turn. Whether these
  are stored as a JSON column or a separate table is decided in architecture.md.
- **Users** gain a timestamp for acknowledging the cloud-model notice.
- One Alembic migration covers all of the above. Pending actions still awaiting confirmation at
  upgrade time are discarded.
- The Qdrant collection's vector size becomes configuration-driven.
- The embedded text of every Qdrant chunk changes to include its source's metadata
  (requirement 7), so all existing points are re-embedded on upgrade. Point payloads keep
  `user_id`, `source_type`, `source_id`, `chunk_index`, `chunk_text`, and `date` for scoping,
  references, and showing dates in the prompt; `date` is no longer used for scoring.
- API keys live only in environment settings — never in the database, logs, traces, or any API
  response.

## Non-functional requirements

- No regression for an existing install: with the default settings (Ollama enabled,
  `gemma4:e2b-it-qat` chat model, `embeddinggemma:300m` embeddings) and the Ollama Compose file
  included, the app behaves as it does today, apart from the intended retrieval change in
  requirement 7.
- All new configuration is environment-variable driven, with the `.env.example` files updated;
  see architecture.md for the specific settings and defaults.
- Automated tests use LangChain's fake chat and embedding models instead of mocking the `ollama`
  client; pytest and Playwright e2e make no network calls to any model provider.
- Opt-in live smoke tests exist per provider; they are skipped when that provider's API key isn't
  set and never run in the default test run.
- Secrets are never sent to the frontend; the `/models` response contains no keys or URLs.
- No specific latency/throughput target beyond prior versions' single-local-user scale; cloud
  latency is governed by the per-provider timeout settings.

## Acceptance criteria for v0.6.0 completion

- No direct `ollama` client imports remain in application code; chat, tool calling, streaming,
  and embeddings go through open-source LangChain, with nothing sent to LangSmith.
- Ollama, Anthropic, OpenAI, and Google Gemini chat models can each be enabled per model through
  environment settings, with startup validation.
- Users can choose an enabled model per conversation, switch it mid-conversation, see which
  model produced each reply, and see whether a model is local or cloud, with a one-time notice
  before first using a cloud model.
- The `pending_action` column and the separate confirmation classifier are gone; todo actions run
  through LangChain tool calling over persisted multi-turn history, including tool calls.
- The scenario suite passes on the default local model, with results recorded in the release
  notes.
- Reasoning output never appears in streamed or stored replies.
- The embedding provider is configurable system-wide, with a documented re-index command.
- Recency re-ranking and its settings are gone; retrieval is pure vector similarity over chunks
  that each embed their full metadata (diary date, title; todo status and dates), and all
  existing data has been re-indexed in that format.
- The stack runs with and without `docker-compose.ollama.yaml`, including on a host without a GPU.
- v0.5.0 observability works across all providers, with provider/model labels on model calls.
- All current-state documentation is updated for the multi-provider setup, and all tests pass.
