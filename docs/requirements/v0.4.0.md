# Requirements — v0.4.0

## Overview

Building on v0.1.0's email/password registration and login, v0.4.0 closes two gaps in account
security and recovery: **mandatory email verification** on signup, and a self-service
**forgot/reset password** flow. Per [../roadmap.md](../roadmap.md), this also includes persisting
the user's language preference on their account — previously a browser-only, `localStorage`-only
setting — specifically so the new verification and password-reset emails can be sent in the
right language from the very first message, rather than defaulting to a single hardcoded
language regardless of who's reading it.

For the technical design supporting these requirements, see [../architecture.md](../architecture.md).

## Goals

- Require every new account to verify its email address via an emailed one-time code before it
  can log in, so a registered address is confirmed reachable rather than merely well-formed.
- Let a user who has forgotten their password reset it via an emailed one-time code, without
  needing support intervention.
- Persist the user's language preference on their account — set at registration, kept in sync
  whenever a signed-in user changes language — so it's no longer purely client-side.
- Send verification and password-reset emails in the account's saved language.
- Keep the SMTP target fully swappable via configuration alone, so self-hosters can point at any
  provider (or a local test server) without a code change.
- Limit how frequently verification/reset emails can be re-requested for the same account, so
  the resend-verification and forgot-password endpoints aren't an open mail-bombing vector
  against an arbitrary inbox.
- Limit how many incorrect codes can be submitted against a single outstanding verification/reset
  code, so a short, human-enterable code isn't brute-forceable by unlimited guessing. This is
  distinct from the login brute-force/lockout protection called out as out of scope below — that
  one's about repeated password guesses against `/auth/login`, this one's about repeated code
  guesses against the new verify/reset endpoints, and is now in scope.

## Non-goals / Out of scope

The following are explicitly **not** part of v0.4.0:

- Broader rate limiting of resend-verification or forgot-password requests beyond a simple
  per-account minimum resend interval — IP-based throttling and sliding-window/backoff counters
  are flagged as a near-term follow-up rather than solved here.
- CAPTCHA on registration or forgot-password.
- Timing-attack resistance on login or forgot-password (not a new regression — login already
  short-circuits on a nonexistent email today without hashing).
- Brute-force or account-lockout protection on login.
- Magic-link (passwordless) login — password-based login is unchanged except for the new
  verification gate.
- Two-factor authentication.
- Changing or re-verifying an email address after the account already exists — email is fixed at
  registration for this version.
- Automatic cleanup of accounts that never complete verification — they simply remain unusable
  until verified, recoverable only via resend.
- A general backend i18n framework — verification/reset email content is a small, hardcoded
  per-locale string set, not a translation system.

## Users

Same as v0.1.0–v0.3.0: each account is independent and self-contained. Nothing in this version
changes cross-account scoping — verification, reset, and locale all act only on the requesting
account's own data.

## Functional requirements

### 1. Verify my email after registering

As the user, after I register, I receive an email with a one-time verification code, and my
account can't log in until I use it.

**Acceptance criteria**
- Registration still creates the account immediately, exactly as today.
- The account remains unverified — and can't log in — until the emailed code is used.
- The email is sent to the address exactly as registered, in the language selected on the
  registration form.

### 2. Login tells me clearly if I haven't verified yet

As the user, if I try to log in before verifying my email, I'm told why, instead of getting the
same error as a wrong password.

**Acceptance criteria**
- An unverified account with the correct password gets a distinct "please verify your email"
  response, not the generic "incorrect email or password" response.
- A wrong password on any account, verified or not, still gets the same generic
  incorrect-credentials response as today — this case is unchanged.

### 3. Complete verification via the emailed code

As the user, entering the verification code from my email verifies my account and signs me in.

**Acceptance criteria**
- A valid, unused, unexpired code marks the account verified and signs me in immediately — no
  separate login step required.
- An expired or already-used code shows a clear error rather than failing silently.
- Submitting too many incorrect codes in a row invalidates the outstanding code, showing the same
  error as an expired/already-used code — no distinct "too many attempts" message.
- Once verified, the account logs in normally like any other account, indefinitely.

### 4. Resend the verification email

As the user, if I didn't receive the verification email or its code expired, I can request a new
one.

**Acceptance criteria**
- Requesting a new verification email invalidates any previous unused code for that account, so
  only the newest one works.
- The response is identical whether or not the given email is registered, or already verified —
  this can't be used to discover which emails have accounts.
- Requesting again before a minimum interval has elapsed since the last verification email was
  sent to that account is a silent no-op — same response, but no new email sent and no code
  invalidated — indistinguishable from the "email not found"/"already verified" no-op cases.

### 5. Request a password reset

As the user who's forgotten my password, I can request a reset code by entering my email.

**Acceptance criteria**
- The response is identical regardless of whether the given email is registered — this can't be
  used to discover which emails have accounts.
- If the email is registered, a reset code is sent to it.
- Requesting again before a minimum interval has elapsed since the last reset email was sent to
  that account is a silent no-op — same response, but no new email sent and no code invalidated —
  indistinguishable from the unregistered-email no-op case.

### 6. Reset my password via the emailed code

As the user, entering the reset code from my email lets me set a new password and signs me back
in.

**Acceptance criteria**
- A valid, unused, unexpired code lets me set a new password and immediately signs me into the
  browser that completed the reset.
- Setting a new password signs me out everywhere else — any other device or browser previously
  logged into the account is signed out.
- An expired or already-used code shows a clear error rather than failing silently.
- Submitting too many incorrect codes in a row invalidates the outstanding code, showing the same
  error as an expired/already-used code — no distinct "too many attempts" message.
- Requesting a new reset code invalidates any previous unused one for that account.

### 7. My account remembers my language

As the user, the language I have selected — at registration, or later while signed in — is saved
to my account, not just kept in my browser.

**Acceptance criteria**
- Registering while the UI is set to a given language saves that language to the new account.
- Changing language while signed in updates the account's saved language, in addition to the
  existing browser-only behavior.
- Changing language while signed out only affects that browser, exactly as today — there's no
  account yet to save it to.

### 8. Verification and reset emails arrive in my language

As the user, the verification and password-reset emails I receive are written in my account's
saved language.

**Acceptance criteria**
- A newly registered account's first verification email is in the language selected on the
  registration form.
- A resend-verification or password-reset email uses the account's currently saved language,
  even if it now differs from what was selected at registration.

### 9. Self-hosters can use any SMTP provider

As the person running Living Genie, I can point it at any SMTP-compatible provider, or a local
test server, purely through configuration.

**Acceptance criteria**
- All SMTP connection details (host, port, credentials, sender address) are environment-variable
  driven; switching providers requires no code change.
- Running locally via `docker compose up` sends verification/reset emails to a local
  mail-catcher by default, so the feature can be developed and tested without a real provider
  account.

## Data requirements

Each user has an email-verification state (whether and when verified), a saved language
preference, and the timestamp of the last verification email and last password-reset email sent
to them (used to enforce the minimum resend interval below), in addition to their existing id,
email, password, and creation timestamp.

Each outstanding verification or reset request is represented by a single-use, expiring code tied
to one user and one purpose (verify or reset), stored hashed rather than in plaintext, with a
bounded number of incorrect-entry attempts before the code is invalidated. Requesting a new code
of a given purpose invalidates any prior outstanding code of that same purpose for that user.

## Non-functional requirements

- SMTP configuration is entirely environment-variable driven — see architecture.md for the
  specific settings and their defaults.
- The minimum resend interval for verification and password-reset emails is environment-variable
  configurable, independently per purpose — see architecture.md for the specific settings and
  their defaults.
- The maximum number of incorrect code-entry attempts before an outstanding verification/reset
  code is invalidated is also environment-variable configurable — see architecture.md for the
  specific setting and its default.
- The full stack, including sending and viewing verification/reset emails, still runs locally via
  `docker compose up`, using a local mail-catcher rather than a real provider account.
- Both frontend and backend must have unit/integration tests covering: the verification-code
  lifecycle (issue, resend/invalidate, expire, consume, lockout after too many incorrect
  attempts), the login gate for unverified accounts, the reset-code lifecycle including session
  invalidation on successful reset, and locale persistence at registration and on later change. No
  specific coverage percentage is required.
- No specific latency/throughput target, consistent with prior versions' single-local-user scale.

## Acceptance criteria for v0.4.0 completion

- Registering an account sends a verification email in the selected language; the account cannot
  log in until that code is used.
- Entering a valid verification code verifies the account and signs the user in; an expired,
  already-used, or too-many-times-wrong code shows a clear error, and a new verification email can
  be requested.
- Requesting a password reset always responds identically regardless of whether the email is
  registered; a valid reset code lets the user set a new password, signs them into the current
  browser, and signs them out of every other session.
- A user's language preference — set at registration or while signed in — is saved to their
  account and used for verification/reset email content.
- The SMTP target is fully configurable via environment variables, and local development requires
  no real provider account.
- Re-requesting a verification or password-reset email before the configured minimum interval has
  elapsed is a silent no-op, indistinguishable from the existing anti-enumeration no-op responses.
