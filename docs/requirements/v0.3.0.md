# Requirements — v0.3.0

## Overview

Building on v0.1.0's diary CRUD and v0.2.0's RAG chatbot, v0.3.0 adds Living Genie's first
non-diary data source: **todos**. Per [../roadmap.md](../roadmap.md), this covers full todo CRUD,
lossless compression of uploaded images, and extending Genie with tool-calling so it can both
answer questions about a user's todos and act on them (create, update, complete, delete) through
chat. Todos become the first realization of the "diary and future data sources" design already
anticipated in v0.2.0 — they're indexed for retrieval the same way diary entries are, so Genie can
answer todo questions grounded in the user's actual data rather than fabricating an answer.

For the technical design supporting these requirements, see [../architecture.md](../architecture.md).

## Goals

- Deliver full todo create/list/view/edit/delete, scoped to the authenticated user, following the
  same pattern diary entries already use.
- Index todos for retrieval automatically, the same way diary entries are, so Genie can answer
  questions grounded in the user's actual todos.
- Extend Genie so it can create, update, complete, or delete todos through natural-language chat,
  confirming with the user before any destructive or state-changing action.
- Make Genie's replies feel less rigid: answer in the model's own words with natural variation in
  phrasing, instead of echoing retrieved excerpts near-verbatim, building on v0.2.0's existing
  anti-verbatim prompt rule.
- Compress uploaded images to the smallest possible size without any loss of visual quality.

## Non-goals / Out of scope

The following are explicitly **not** part of v0.3.0:

- Due-date reminders or notifications of any kind.
- Recurring todos.
- Priority levels, tags, subtasks, or any todo metadata beyond title/description/due date/completed.
- Undoing a chat-confirmed action (e.g. "undo that delete") — a confirmed action is final, same as
  a confirmed delete already is in the UI.
- A dedicated confirm/cancel button UI in chat — confirmation before a destructive or
  state-changing chat action happens conversationally (the user replies to confirm), not through
  new client-side UI state.
- A separate chat tool for *looking up* todos — Genie answers todo questions using the same
  retrieval mechanism it already uses for diary questions; tool-calling is used only for actions
  that change data.
- Backfilling or recompressing images uploaded under v0.1.0/v0.2.0 — compression applies to new
  uploads only.
- Any change to diary CRUD, authentication, or conversation management themselves, beyond the
  shared-infrastructure generalization described in architecture.md.

## Users

Same as v0.1.0/v0.2.0: each authenticated account's todos, conversations, and retrieval are scoped
strictly to that account. One account can never see, retrieve, or act on another account's todos,
whether through the UI or through chat.

## Functional requirements

### 1. Create a todo

As the user, I can create a todo with a **title** (required), an optional **description**, and an
optional **due date**.

**Acceptance criteria**
- A todo cannot be saved without a title.
- The todo is persisted and immediately visible in the todo list after creation, owned by the
  authenticated account.

### 2. View the list of todos

As the user, I can see all my todos in a list.

**Acceptance criteria**
- The list only ever includes the authenticated account's own todos.
- Both pending and completed todos are visible in the list (completion is a status, not a filter
  that hides items by default).

### 3. View and edit a todo

As the user, I can open a todo and edit its title, description, and/or due date.

**Acceptance criteria**
- Saving an edit updates the todo in place and refreshes its `updated_at` timestamp.
- Only the todo's owning account can view or edit it; another account's attempt behaves
  identically to acting on a nonexistent todo.

### 4. Mark a todo complete

As the user, I can toggle a todo between pending and completed.

**Acceptance criteria**
- Toggling completion is a distinct, one-step action (e.g. a checkbox) — it doesn't require
  opening the full edit form.
- Only the owning account can toggle it; another account's attempt behaves identically to acting
  on a nonexistent todo.

### 5. Delete a todo

As the user, I can delete a todo, with a confirmation step to prevent accidental loss.

**Acceptance criteria**
- Once confirmed, the todo is removed and no longer appears in the list.
- Only the owning account can delete it; another account's delete attempt behaves identically to
  deleting a nonexistent todo.

### 6. Todos are indexed automatically

As the user, when I create, edit, or complete/uncomplete a todo, it's indexed for retrieval in the
background, without blocking the save action — the same guarantee diary entries already have.

**Acceptance criteria**
- Saving a todo (create, edit, or completion toggle) returns immediately; indexing happens
  asynchronously afterward.
- If the app restarts before indexing finishes, indexing resumes/completes without user action.

### 7. Deleting a todo removes it from retrieval

As the user, once I delete a todo, Genie can no longer reference it in chat.

**Acceptance criteria**
- After deletion, the todo's content is excluded from future retrieval.

### 8. Ask Genie about my todos

As the user, I can ask Genie a question about my todos (e.g. "what's due this week?", "have I
already bought milk?") in an existing or new conversation.

**Acceptance criteria**
- Genie answers using relevant retrieved todos when available, citing which todo(s) it drew from,
  the same way it already cites diary entries.
- If no relevant todo exists, Genie says so rather than fabricating an answer.
- A single conversation can mix diary and todo questions naturally — Genie isn't a separate
  "todo mode."

### 9. Manage my todos through chat

As the user, I can ask Genie to create, update, mark complete, or delete a todo using natural
language, without leaving the conversation.

**Acceptance criteria**
- Creating a todo through chat happens without requiring a separate confirmation step.
- Updating, completing, or deleting a todo through chat requires Genie to confirm which todo and
  the intended action with the user first; the action only happens after the user confirms in a
  following message.
- After performing an action, Genie's reply states what it did and includes a link to the
  affected todo so the user can quickly verify the result.
- Genie only acts on the requesting user's own todos.

### 10. Genie stays scoped to diary, todos, and app help

As the user, if I ask Genie something unrelated to my diary, my todos, or how Living Genie works,
it declines to answer rather than acting as a general-purpose assistant.

**Acceptance criteria**
- This extends v0.2.0's existing scope-guarding requirement to include todos as a third in-scope
  topic; the firm-rejection behavior for out-of-scope requests is unchanged.

### 11. Uploaded images are compressed losslessly

As the user, when I insert an image into a diary entry, it's stored at the smallest size possible
without any visible loss of quality compared to what I uploaded.

**Acceptance criteria**
- A newly uploaded image is smaller on disk than the raw uploaded file wherever compression can
  reduce size, with no perceptible change in the image's visual appearance.
- Uploading a file that isn't a valid image fails with a clear error rather than being stored.
- Only applies to uploads made from v0.3.0 onward — existing images already on disk are
  unaffected.

## Data requirements

Each todo has: an id, the owning user, a title, an optional description, an optional due date, a
completed flag, and created/updated timestamps.

Each indexed todo chunk conceptually needs the same shape as an indexed diary chunk: a reference
to its source todo, the owning user, the chunk's text, and its embedding vector — see
architecture.md for how this is generalized across both source types rather than duplicated.

Each assistant message may reference one or more todos or diary entries it drew from or acted on
— see architecture.md's generalized message-reference design.

## Non-functional requirements

- The full stack, including todo indexing, still runs locally via `docker compose up` — no new
  containers/services are required for todos, tool-calling, or image compression.
- Tool-calling reliability against the locally-hosted chat model is not guaranteed by any specific
  model choice; validate during implementation and re-pin `OLLAMA_CHAT_MODEL` if the currently
  configured model proves unreliable at following the confirm-before-acting rule.
- No specific latency/throughput target, consistent with v0.1.0/v0.2.0's single-local-user scale.
- Both frontend and backend must have unit/integration tests covering: todo CRUD and scoping, todo
  indexing triggers (create/edit/complete/delete), retrieval over a mix of diary and todo content,
  and chat-driven todo actions (including the confirm-before-acting behavior). No specific
  coverage percentage is required.

## Acceptance criteria for v0.3.0 completion

- Through the UI, the user can create, list, view, edit, complete/uncomplete, and delete todos
  end-to-end.
- Creating, editing, or completing a todo results in it becoming retrievable by Genie once
  background indexing completes; deleting a todo removes it from what Genie can reference.
- Through the chat UI, the user can ask Genie a question grounded in their own todos and get a
  cited answer, or an honest "nothing relevant" response.
- Through the chat UI, the user can ask Genie to create a todo directly, and to update, complete,
  or delete one after confirming — with Genie's reply linking to the affected todo.
- Newly uploaded images are visibly smaller on disk than the raw upload with no loss of quality.
