# Requirements — v0.5.0

## Overview

Building on v0.1.0–v0.4.0's feature set, v0.5.0 adds operational visibility: structured logging,
metrics, and distributed tracing across the backend (`web-api`) and `worker`, surfaced through a
self-hosted Grafana stack. Today the API/worker only use ad-hoc, unstructured
`logging.getLogger` calls (only `worker.py` configures `logging.basicConfig`), and there is no
metrics endpoint, no tracing, and no way to see how a request or background job actually behaves
beyond eyeballing container logs. This version closes that gap so the self-hoster running
`docker compose up` can see request/job health, drill into individual slow or failing requests,
and correlate logs with the trace that produced them — without needing a third-party account,
consistent with the rest of the app's self-hosted, single-VM deployment model.

For the technical design supporting these requirements, see [../architecture.md](../architecture.md).

## Goals

- Replace ad-hoc stdlib logging in `web-api` and `worker` with structured (JSON) logs that
  include a trace/span ID for correlation.
- Expose Prometheus-compatible metrics (request rate, error rate, latency; background job counts
  and durations) from both `web-api` and `worker`.
- Instrument `web-api` and `worker` with distributed tracing (OpenTelemetry) covering calls to
  Postgres, Qdrant, and Ollama, so a single request or job's time can be broken down by where it
  was spent.
- Give the app's two most complex pipelines — the chat/RAG request flow (embed query → vector
  search → prompt build → LLM call → each tool-call execution in the multi-turn loop) and the
  worker's per-job pipeline (chunk → embed each chunk → Qdrant upsert) — their own named custom
  spans, not just the generic HTTP/DB/outbound-call spans auto-instrumentation provides, since
  those are the parts of the app most worth being able to break down when they're slow.
- Run a self-hosted observability stack — Prometheus (metrics), Loki (log aggregation), Tempo
  (traces), Grafana (dashboards) — as additional services in the existing `docker-compose.yaml`,
  with no external accounts or data leaving the host.
- Provide Grafana dashboards that let a click from a slow/erroring request's trace jump to its
  correlated logs and relevant metrics.
- Keep the stack's storage/retention and service endpoints environment-variable configurable,
  consistent with how the rest of the app is configured.

## Non-goals / Out of scope

The following are explicitly **not** part of v0.5.0:

- Hosted/SaaS observability backends (Grafana Cloud, Datadog, etc.) — self-hosted only for this
  version.
- Alerting and notification channels (email/Slack/etc. alerts on metric thresholds) — dashboards
  only; alerting is flagged as a near-term follow-up.
- Frontend (`web/`) instrumentation — this version covers the backend and worker only.
- High-availability or clustered deployment of the observability stack — single-instance
  containers, matching the rest of the app's single-VM model.
- Long-term log/metric/trace retention tuning beyond sensible defaults — retention is
  configurable but not a subject of this version's requirements.
- Business/product analytics (e.g. usage dashboards, diary/todo counts) — this version is about
  operational health, not product metrics.
- Sampling or cost-control strategies beyond a single configurable trace-sampling rate — no
  adaptive sampling.

## Users

This version has one audience: the person self-hosting and operating Living Genie (today, that's
the same person as the end user). Nothing here is exposed to or changes behavior for diary/todo
end users.

## Functional requirements

### 1. See structured logs from the backend and worker

As the person running Living Genie, I can view structured (JSON) logs from `web-api` and
`worker` in Grafana, instead of reading raw container output.

**Acceptance criteria**
- All logging in `web-api` and `worker` goes through a shared structured-logging setup
  (replacing the current stdlib `logging.getLogger` + single `basicConfig` call in `worker.py`).
- Each log line includes at minimum: timestamp, level, logger/module name, message, and (when
  inside a request or job) a trace ID and span ID.
- Logs are shipped to Loki and viewable/searchable in Grafana's Explore view.

### 2. See request and job metrics

As the person running Living Genie, I can see request rate, error rate, and latency for
`web-api`, and job counts/durations for `worker`, in Grafana.

**Acceptance criteria**
- `web-api` exposes a `/metrics` endpoint in Prometheus text format with, at minimum, per-route
  request count, error count, and latency histogram.
- `worker` exposes equivalent metrics for job counts, failures, and durations, broken down by
  `source_type` (`diary_entry` / `todo`).
- Chat-specific metrics are included, not just generic request counts: tool calls executed,
  broken down by tool name and whether `user_confirmed` gated them, and RAG retrieval latency
  (the Qdrant similarity-search step) as its own histogram.
- Prometheus is configured to scrape both, and a Grafana dashboard visualizes them out of the
  box.

### 3. Trace a request or job end-to-end

As the person running Living Genie, I can pick a slow or failing request/job in Grafana and see
a trace showing where its time was spent across the API, worker, Postgres, Qdrant, and Ollama.

**Acceptance criteria**
- `web-api` and `worker` are instrumented with OpenTelemetry, exporting spans to Tempo.
- A trace for a given request/job includes child spans for its Postgres queries, Qdrant calls,
  and Ollama calls (when applicable).
- From a trace in Grafana, I can jump directly to the logs emitted during that same
  request/job (via the shared trace ID).

### 4. Break down a chat request by pipeline stage

As the person running Living Genie, when a `POST /conversations/{id}/messages` call is slow or
produces a wrong/unexpected tool action, I can see a trace with a distinct span for each stage of
the pipeline: embedding the query, the Qdrant similarity search, building the prompt, each Ollama
chat call in the tool-calling loop, and each individual tool execution (`create_todo`,
`update_todo`, `complete_todo`, `delete_todo`) with its `user_confirmed` outcome.

**Acceptance criteria**
- Each stage above appears as its own named span, not merged into one generic "handle request"
  span.
- A tool-call span records which tool was called and whether it actually executed (i.e. whether
  `user_confirmed` gated it) — without logging the conversation content itself.
- The number of tool-calling loop iterations for a given request is visible on the trace (e.g. as
  span count or an attribute), to help debug the loop's iteration cap being hit.

### 5. Break down an indexing job by pipeline stage

As the person running Living Genie, when an `embedding_jobs` row is slow or fails, I can see a
trace with a distinct span for chunking the source content, embedding each chunk, and the Qdrant
upsert, rather than one opaque "process job" span.

**Acceptance criteria**
- Chunking, per-chunk (or batched) embedding, and the Qdrant upsert each appear as their own
  span, tagged with the job's `source_type` and `source_id`.
- A failed job's trace shows which stage it failed at, matching the existing `error_message`
  column's failure rather than requiring a log correlation to find out.

### 6. Run the full observability stack locally with no external accounts

As the person running Living Genie, `docker compose up` gives me a working Grafana instance with
logs, metrics, and traces already flowing — no signup, API key, or external service required.

**Acceptance criteria**
- Prometheus, Loki, Tempo, and Grafana run as additional services in `docker-compose.yaml` (and,
  where relevant, the dev overlay).
- Grafana comes pre-provisioned with the Prometheus/Loki/Tempo data sources and at least one
  dashboard, so there's no manual setup step after `docker compose up`.
- No telemetry data leaves the host by default.

### 7. Configure the observability stack without code changes

As the person running Living Genie, I can adjust retention, service endpoints, and trace
sampling rate via environment variables.

**Acceptance criteria**
- Log/metric/trace retention periods are environment-variable configurable with sensible
  defaults.
- The OpenTelemetry exporter endpoint and trace sampling rate are environment-variable
  configurable.
- No source change is required to point any component at a different endpoint or adjust these
  values.

## Data requirements

Telemetry data is operational, not user data: structured JSON log lines (timestamp, level,
logger, message, trace/span ID, free-form context fields) stored in Loki; Prometheus-format
counter/histogram time series for requests and jobs stored in Prometheus; and OpenTelemetry
spans (with parent/child relationships spanning API, worker, Postgres, Qdrant, and Ollama calls)
stored in Tempo, linked across all three by a shared trace ID. None of this is scoped per
end-user account — it describes system behavior, not diary/todo content.

## Non-functional requirements

- The full stack, including Prometheus, Loki, Tempo, and Grafana, still runs locally via
  `docker compose up`, with Grafana pre-provisioned — no manual dashboard/data-source setup.
- Retention periods, OpenTelemetry exporter endpoint, and trace sampling rate are
  environment-variable configurable — see architecture.md for the specific settings and their
  defaults.
- Tracing instrumentation must not introduce noticeable latency under the app's existing
  single-local-user scale; a configurable sampling rate is provided as the lever if needed
  rather than a hard performance target.
- Both `web-api` and `worker` should have tests confirming: logs are emitted in the expected
  structured format, the `/metrics` endpoints return valid Prometheus-format output, and tracing
  spans are created for representative request/job paths.
- No specific latency/throughput target beyond the above, consistent with prior versions'
  single-local-user scale.

## Acceptance criteria for v0.5.0 completion

- `web-api` and `worker` emit structured JSON logs (with trace/span IDs) instead of the current
  unstructured stdlib logging.
- `web-api` and `worker` each expose a working Prometheus metrics endpoint, scraped by a
  Prometheus instance running in `docker-compose.yaml`.
- Requests and jobs are traced end-to-end via OpenTelemetry/Tempo, including their Postgres,
  Qdrant, and Ollama calls, with the chat/RAG pipeline and the worker's chunk/embed/upsert
  pipeline each broken into their own named spans rather than one opaque span per request/job.
- Grafana runs locally via `docker compose up`, pre-provisioned with the Prometheus/Loki/Tempo
  data sources and at least one dashboard, letting a trace be correlated to its logs.
- All new configuration (retention, exporter endpoint, sampling rate) is environment-variable
  driven, with no external accounts required for local operation.
