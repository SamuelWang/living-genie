# Execution plan — v0.3.0

Ordered task breakdown for implementing v0.3.0, sequencing the work described in
[../architecture.md](../architecture.md) against the acceptance criteria in
[../requirements/v0.3.0.md](../requirements/v0.3.0.md). This doc tracks *what to build and in what
order*, not design decisions — those live in architecture.md.

Confirmed decisions (see architecture.md for anything not called out here):
- **Generalize, don't duplicate**: the indexing/retrieval pipeline (`embedding_jobs`, the Qdrant
  collection, the worker, and assistant-message references) is reshaped to be source-type-generic
  across diary entries and todos, rather than adding a parallel todo-specific copy alongside the
  existing diary-specific one.
- **Reads vs. writes**: todo *questions* go through the same retrieval pipeline as diary Q&A (no
  dedicated lookup tool); todo *mutations* go through tool-calling exclusively.
- **Confirmation is conversational, not UI state**: `update_todo`/`complete_todo`/`delete_todo`
  require a `user_confirmed` tool argument that the backend mechanically gates on; there's no
  confirm/cancel button — the model asks, the user replies, the model calls again.
- **Compression format**: PNG/other lossless sources → WebP lossless; JPEG sources stay JPEG,
  re-optimized losslessly (`quality="keep"`).
- **Chat tone tuning bundled into this pass**: since Section 5.1 already rewrites
  `build_system_prompt()`/`generate_reply_stream()` for todo tool-calling, the existing
  "replies feel rigid / repeat excerpts verbatim" feedback is addressed in the same touchpoint —
  explicit Ollama decoding `options` plus warmer persona wording — rather than as a separate pass.

Remaining implementation-detail parameters (tool-loop iteration cap, whether a due-date-only edit
should re-embed a todo, the exact todo chunk-text composition, etc.) are given reasonable defaults
inline, flagged `(tune)` — to be confirmed/adjusted during implementation rather than blocking this
plan.

   `embedding_chunk_size`/`embedding_chunk_overlap`/`retrieval_top_k`/etc. tunables unchanged.
   Also add decoding-parameter tunables for the chat call, currently left at Ollama/model
   defaults: `ollama_chat_temperature: float = 0.9` and `ollama_chat_repeat_penalty: float = 1.3`
   `(tune)`. Only one of temperature/top_p is exposed — standard sampling guidance (e.g. OpenAI's
   API docs) is to tune temperature or top_p, not both at once, since they both govern overall
   randomness and adjusting them together makes it hard to isolate cause and effect; top_p is left
   at the model's default. `repeat_penalty` is a separate axis (repetition suppression, not overall
   randomness) so it's tuned independently — it in particular discourages the model from
   regenerating spans of text already present in the prompt (i.e. the injected excerpts), directly
   targeting the verbatim-repeat complaint.
