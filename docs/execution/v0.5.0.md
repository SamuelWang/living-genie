# Execution plan — v0.5.0

Ordered task breakdown for implementing v0.5.0, sequencing the work against the acceptance
criteria in [../requirements/v0.5.0.md](../requirements/v0.5.0.md). Unlike prior versions,
[../architecture.md](../architecture.md) doesn't yet describe v0.5.0's design — that doc describes
"the system as it currently stands," so it's only updated once this version is actually built (see
Section 10). Until then, this doc is the working source of truth for v0.5.0's technical design as
well as its task breakdown.

Confirmed decisions:
- **`structlog` for structured logging, replacing every ad-hoc `logging.getLogger`** — a single
  shared setup emits JSON lines to stdout for both `web-api` and `worker`, rather than each module
  configuring its own logger (only `worker.py` currently calls `logging.basicConfig`).
- **Grafana Alloy — not Promtail — is the log-shipping agent, receiving logs via OTLP push, not
  by tailing Docker's stdout driver.** Promtail reached EOL in March 2026; Alloy is Grafana's
  OpenTelemetry Collector distribution and its official successor. Rather than a like-for-like
  swap (Alloy tailing `json-file` logs the way Promtail did), `structlog` gets an OTel
  `LoggingHandler` alongside its existing stdout JSON handler, so logs travel the same
  OTLP-over-gRPC path the app already uses for traces (Section 1's `otel_exporter_otlp_endpoint`,
  now pointed at `alloy:4317` instead of `tempo:4317`). Alloy receives both signals on one
  `otelcol.receiver.otlp` and fans them out — traces to Tempo, logs to Loki's native OTLP
  ingestion endpoint. This drops the Docker-socket-mount + `json-file`-tailing indirection
  entirely, and gives Loki real `trace_id`/`span_id` structured metadata on ingest instead of
  parsing it out of a JSON field. Stdout JSON output is unchanged — still emitted, still useful
  for `docker compose logs`; this only changes how logs additionally reach Loki.
- **`worker` gets its own bare `prometheus_client` HTTP server** — unlike `web-api`, which already
  has an ASGI app to hang `prometheus-fastapi-instrumentator` off of, `worker` has no existing HTTP
  server, so its `/metrics` port is a small standalone server started alongside the polling loop.
- **Auto-instrumentation first, hand-instrumented spans only where it doesn't reach** — FastAPI,
  SQLAlchemy, and outbound HTTP (both `qdrant-client` and the `ollama` client are `httpx`-based, so
  `opentelemetry-instrumentation-httpx` covers both) give generic request/DB/outbound-call spans
  for free; the chat/RAG pipeline and the worker's chunk/embed/upsert pipeline each get their own
  named custom spans on top, since those are the two places auto-instrumentation alone wouldn't
  explain where time actually went.
- **No new Postgres tables** — telemetry (logs, metrics, traces) lives in Loki/Prometheus/Tempo,
  not the app database; this version needs no Alembic migration.
- **Frontend is out of scope** — `web/` is not instrumented in this version, per requirements.md's
  non-goals.

Remaining implementation-detail parameters (exact custom-span/metric naming, the starter Grafana
dashboard's panel set, whether OTLP export uses gRPC or HTTP) are given reasonable defaults inline,
flagged `(tune)`, to be confirmed/adjusted during implementation rather than blocking this plan.

## 1. Infra & configuration

1. [x] `web-api/pyproject.toml` — add to main dependencies (shared by `worker`, same image):
   `structlog`, `prometheus-fastapi-instrumentator`, `prometheus-client`, `opentelemetry-sdk`
   (its `opentelemetry.sdk._logs` module provides the logs API/SDK — `LoggerProvider`,
   `LoggingHandler` — used alongside the tracing SDK, so this one package covers both signals),
   `opentelemetry-exporter-otlp` `(tune)` (gRPC vs. HTTP OTLP exporter package — default to
   `opentelemetry-exporter-otlp-proto-grpc`, matching Alloy's default receiver; this package's
   `OTLPLogExporter` is reused for the logs signal too, so no separate logs-exporter package is
   needed), and the instrumentation packages `opentelemetry-instrumentation-fastapi`,
   `opentelemetry-instrumentation-sqlalchemy`, `opentelemetry-instrumentation-httpx`.
2. [x] `web-api/app/settings.py` — add new settings: `otel_exporter_otlp_endpoint: str =
   "http://alloy:4317"` (used for both trace and log export — Alloy is the single OTLP ingestion
   point that fans traces out to Tempo and logs out to Loki; see Section 7), `otel_traces_sampler_
   ratio: float = 1.0` `(tune)` (1.0 = sample everything, reasonable at this project's
   single-local-user scale; exposed so it can be lowered without a code change), `worker_metrics_
   port: int = 9101`, `prometheus_retention: str = "15d"`, `loki_retention_period: str = "168h"`
   (7d, Loki's duration format), `tempo_retention: str = "336h"` (14d) — retention settings are
   consumed by the Compose/service config files in Section 7, not by application code, but are
   centralized here so every env-var default lives in one place per the project's existing
   convention.
3. [x] `web-api/.env.example` and any `worker`-specific env file — add the corresponding
   `SCREAMING_SNAKE_CASE` env vars (`OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_TRACES_SAMPLER_RATIO`,
   `WORKER_METRICS_PORT`, `PROMETHEUS_RETENTION`, `LOKI_RETENTION_PERIOD`, `TEMPO_RETENTION`),
   matching the existing convention.
4. [x] `docker-compose.yaml` — expose `worker`'s new metrics port so Prometheus (added in Section
   7) can scrape it; no other wiring changes needed here (the observability services themselves are
   added in Section 7, kept separate so this section stays scoped to app-level config).

## 2. Backend & worker: observability bootstrap

Depends on Section 1 (new settings must exist).

1. [x] New shared module, e.g. `web-api/app/observability.py` (flat layout matching
   `embeddings.py`/`chunking.py`/`email.py`):
   - [x] `configure_tracing(service_name: str) -> None` — builds an OpenTelemetry `TracerProvider`
     with a `Resource` carrying `service.name` (`"web-api"` / `"worker"`, so Tempo/Grafana can tell
     the two apart), a `TraceIdRatioBased(settings.otel_traces_sampler_ratio)` sampler, and an OTLP
     span exporter pointed at `settings.otel_exporter_otlp_endpoint`; sets it as the global tracer
     provider via `trace.set_tracer_provider(...)`.
   - [x] `configure_logging() -> None` — configures `structlog` to render JSON to stdout via
     stdlib `logging`'s root handler (so uvicorn/other stdlib loggers are captured too), with a
     processor chain that pulls the current span's `trace_id`/`span_id` (via
     `opentelemetry.trace.get_current_span()`) into each log event when one is active. Also builds
     an OTel `LoggerProvider` with the same `Resource(service.name=...)` used by
     `configure_tracing()`, wraps a `BatchLogRecordProcessor(OTLPLogExporter(endpoint=settings.
     otel_exporter_otlp_endpoint))` into it, sets it globally via `set_logger_provider(...)`, and
     attaches `LoggingHandler(logger_provider=...)` to the same stdlib root logger alongside the
     stdout handler — so every log record reaches both the stdout JSON sink and Alloy over OTLP.
     Unlike the stdout sink's manual `trace_id`/`span_id` processor, the OTLP sink's
     `LoggingHandler` attaches the active span's context to each emitted log record automatically.
     Must run *after* `configure_tracing()`, since both the stdout processor and the OTLP handler
     read the active span/tracer provider.
   - [x] `get_logger(name: str)` — thin wrapper around `structlog.get_logger(name)`, exported so
     call sites can do a one-line swap from `logging.getLogger(__name__)`.
2. [x] `web-api/app/main.py` — call `configure_tracing("web-api")` then `configure_logging()` at
   module import time / app startup (before any router imports that might log), replacing any
   ad-hoc `logging` setup.
3. [x] `worker.py` — replace the existing `logging.basicConfig(...)` call with
   `configure_tracing("worker")` then `configure_logging()`, called once at process start before
   the polling loop begins. (Note: the module is actually `web-api/app/worker.py`, run via
   `python -m app.worker`, not a repo-root script.)
4. [x] Sweep `web-api/app/*.py` and `worker.py` for existing `logging.getLogger(__name__)` call
   sites and replace with `observability.get_logger(__name__)`, so every log line goes through the
   shared structured setup. (Also swept `web-api/app/routers/conversations.py`, outside the literal
   flat glob but with the same call site, to fully satisfy the "every log line" goal.)

## 4. Backend: chat/RAG custom spans + business metrics

Depends on Section 3. Targets `POST /conversations/{id}/messages`'s handler
(`web-api/app/routers/conversations.py` or wherever the chat pipeline lives).

1. [x] Add a module-level `tracer = trace.get_tracer(__name__)` and wrap each pipeline stage in its
   own named `with tracer.start_as_current_span("chat.embed_query"): ...` (and similarly
   `chat.qdrant_search`, `chat.build_prompt`) so each appears as a distinct child span rather than
   being absorbed into the generic FastAPI request span.
2. [x] Wrap each Ollama chat call inside the tool-calling loop in its own
   `chat.ollama_call` span, with an attribute recording the loop iteration number — so the number
   of tool-calling loop iterations for a given request is visible on the trace (per requirement 4),
   useful for debugging the iteration cap being hit.
3. [x] Wrap each individual tool execution (`create_todo`/`update_todo`/`complete_todo`/
   `delete_todo`) in a `chat.tool_call` span tagged with `tool.name` and `tool.user_confirmed`
   (bool) — recording whether the call actually executed or was gated, without logging the
   conversation content itself.
4. [x] New Prometheus metrics (via `prometheus_client`, registered against the same registry
   `prometheus-fastapi-instrumentator` uses so they're exposed on the same `/metrics` endpoint): a
   `Counter` for tool calls (labels: `tool_name`, `user_confirmed`) and a `Histogram` for RAG
   retrieval latency (the Qdrant similarity-search step specifically, not the whole request).

## 9. Final acceptance walkthrough

Driven against `docs/requirements/v0.5.0.md`'s "Acceptance criteria for v0.5.0 completion" list,
mirroring v0.4.0's Section 10 precedent (a live pass against a running `docker compose` stack) —
with the same isolation requirement `CLAUDE.md` establishes: this must run against a throwaway,
isolated Compose project (its own project name, remapped ports, its own Postgres database), never
the real dev stack on ports 8000/5173 or the `living_genie` database, and never left running
afterward.

   (requirement 1) — both via `docker compose logs` (stdout sink, unchanged) and via Grafana's
   Explore view once Loki is confirmed reachable (now arriving via OTLP through Alloy rather than
   Promtail).
3. [ ] Confirm Prometheus's targets page shows both `web-api` and `worker` as `UP`, and that
   Grafana's pre-provisioned dashboard renders request/error/latency and job count/duration panels
   with real data from a few exercised requests/jobs (requirement 2, 6).
4. [ ] Drive one chat request (through the UI or directly) that triggers the tool-calling loop and
   confirm its trace in Grafana/Tempo shows the distinct `chat.*` spans from Section 4, including a
   tool-call span's `user_confirmed` attribute, and that clicking through from the trace reaches
   the correlated log lines via the shared trace ID (requirement 3, 4).
5. [ ] Trigger one diary/todo indexing job and confirm its trace shows the distinct `job.*` spans
   from Section 6, tagged with the correct `source_type`/`source_id` (requirement 5).

   environment-variable driven with no source change needed to adjust them (requirement 7).
