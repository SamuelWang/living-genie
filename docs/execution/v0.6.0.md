# Execution plan — v0.6.0

Ordered task breakdown for implementing v0.6.0, sequenced against the acceptance criteria in
[../requirements/v0.6.0.md](../requirements/v0.6.0.md). As with v0.5.0,
[../architecture.md](../architecture.md) doesn't describe v0.6.0's design yet. It describes the
system as it currently stands, so it is updated only once this version is built (see Section 17).
Until then, this doc is the working source of truth for v0.6.0's technical design as well as its
task breakdown.

Confirmed decisions:
- **LangChain v1's `create_agent` is the agent loop.** It runs `bind_tools` on the selected chat
  model, executes tool calls, feeds `ToolMessage` results back, and stops when the model answers
  without tool calls. It builds on the open-source `langgraph` package, which is a dependency of
  `langchain`. LangGraph Platform/LangSmith are not used. `CHAT_TOOL_MAX_ITERATIONS` maps to the
  graph's `recursion_limit` (`2 * iterations + 1` `(tune)`: one model step plus one tool step per
  iteration, plus the final answer). Chat models are built with `init_chat_model`.
- **Model registry in a new `app/llm.py`** (flat layout, named so it doesn't collide with
  `models.py`).
  - Model ids are `provider:model`, split on the **first** `:` because Ollama tags contain
    colons (`ollama:gemma4:e2b-it-qat`).
  - App provider ids are `ollama`, `anthropic`, `openai` and `google`. `google` maps to
    LangChain's `google_genai`.
  - `ollama` is `local` and the other three are `cloud`.
- **Chat memory is one row per LangChain message.**

  *Why the schema has to change.* Today `messages` holds one row per user message and one per
  final assistant reply, ordered by `created_at`. That doesn't fit the new mechanism:
  - A LangChain turn is a chain: `HumanMessage` → `AIMessage(tool_calls)` → `ToolMessage` … →
    `AIMessage(text)`. The steps in the middle have nowhere to live.
  - `created_at` is `server_default=func.now()`, which is the *transaction* start time. All rows
    a turn writes in one transaction would share a timestamp, so their order would be lost.
  - Nothing records which model wrote a reply.

  *New shape.* Each LangChain message gets its own `messages` row, mapped 1:1:
  - `role`: `user` (Human), `assistant` (AI) or `tool` (Tool).
  - `content`: plain text.
  - `tool_calls`: JSONB `[{id, name, args}]`, on assistant rows that called tools.
  - `tool_call_id` and `tool_name`: on tool rows.
  - `model`: on assistant rows.
  - `seq`: a `BIGINT` identity column that becomes the ordering key everywhere.

  *Rules.*
  - Content is normalized to text before saving, with no reasoning or provider content blocks.
  - Tool-call ids are rewritten to app-generated `call_<hex>` ids. Providers require each
    `ToolMessage.tool_call_id` to match a call in the `AIMessage` just before it. Ollama returns
    no ids and Anthropic restricts the id format, so this keeps history replayable to any
    provider after a mid-conversation switch.
  - The system prompt and the retrieved excerpts are rebuilt every turn and never stored.

  *Rejected alternatives.*
  - A JSONB message array on `conversations`. It breaks the `message_references` FK, rewrites
    the whole history on every turn, and risks lost updates when two sends happen at once.
    Compacting it later would also erase the transcript the UI shows.
  - A JSONB "agent steps" blob on the reply row, which would be a second message format inside
    the message table.
  - LangGraph's Postgres checkpointer. Its opaque state blobs live in tables outside Alembic, with
    no FK to `users`/`conversations`. They would duplicate `messages` and persist the current-turn
    excerpts and raw provider content blocks.
- **Conversation compaction and a LangGraph checkpointer are deferred.** History depth stays
  bounded by `CHAT_CONTEXT_TURNS`. Both are recorded in architecture.md's "Future
  considerations" (Section 17.3).
  - Compaction would add `conversations.memory_summary` and `memory_summary_through_seq`, so
    history becomes the summary plus the rows after it, with the transcript rows untouched.
  - A checkpointer would key threads by `conversation.id` and be seeded from the existing rows.
    It's worth adopting if interrupt-based tool approval or long-running agents arrive.
- **The server enforces the cloud-model notice.** A send whose *effective* model is cloud fails
  with `409 {"detail": {"code": "cloud_notice_required"}}` until
  `users.cloud_model_notice_acknowledged_at` is set. This also covers a cloud
  `DEFAULT_CHAT_MODEL` the user never actively picked. The UI shows the notice when a cloud model
  is selected, and on that 409.
- **A disabled stored model falls back on send, but an explicit choice is validated.** If a
  conversation's stored `chat_model` has since been disabled, the next send uses
  `DEFAULT_CHAT_MODEL` and the UI says so. An unknown or disabled id is rejected with `422` only
  when it is set explicitly (`POST`/`PATCH /conversations`).
- **`*_ENABLED` switches govern chat models only.** `EMBEDDING_PROVIDER` uses that provider's
  key/URL setting whether or not its chat switch is on, so cloud chat can be disabled while still
  embedding with that provider.
- **SSE contract changes:**
  - `references` can be emitted more than once: retrieval refs before any tokens, then again
    after tool results add mutated todos. Each event carries the full current list, and the
    frontend replaces what it has.
  - Only `text` content blocks become `token` events. Reasoning blocks (Anthropic thinking,
    Gemini thoughts, Ollama `reasoning_content`) are dropped.
  - `error` gains a `code`: `provider_auth`, `rate_limited`, `timeout`, `provider_error` or
    `iteration_limit`.
- **A test-only `fake` provider keeps e2e off real models.** It is enabled only by
  `FAKE_LLM_ENABLED=true`, which the Playwright webServer sets. It is never in `.env.example`
  and never documented as a user feature, and startup refuses `fake:*` ids without the flag. It
  offers `fake:local-echo` (local) and `fake:cloud-echo` (cloud): keyword-scripted models, so e2e
  can cover the model selector, switching and the cloud notice through the real server.
  `EMBEDDING_PROVIDER=fake` uses `DeterministicFakeEmbedding`. pytest uses LangChain's fake
  models directly (Section 11).
- **One temperature per provider.** The separate low tool-decision temperature
  (`OLLAMA_TOOL_TEMPERATURE`) is dropped, since one agent model runs every step of a turn.
  `OLLAMA_TEMPERATURE` defaults to `0.3`, the value `.env.example` already uses `(tune)`.
- **Every chunk embeds a metadata header.** A chunk's embedded text is a source-metadata header
  plus a body chunk, repeated on every chunk of the source. The body is chunked to
  `chunk_size - len(header)` so header plus body fits `EMBEDDING_CHUNK_SIZE`. Qdrant's
  `chunk_text` payload stores the full header plus body, so the prompt sees the metadata too.

Remaining implementation-detail parameters are given reasonable defaults inline and flagged
`(tune)`. They are to be confirmed or adjusted during implementation rather than blocking this
plan. They include:
- each provider's default timeout and retry values
- the header-length floor
- how the embedding fingerprint is stored in Qdrant
- whether a CHECK constraint guards `messages.role`

## 4. Backend: metadata-rich chunks + pure-vector retrieval

Depends on Section 3.

1. [ ] `web-api/app/chunking.py` — new `compose_chunks(source_type, source, chunk_size, overlap)
   -> list[str]`, which prepends a header to every chunk:
   - **Diary entry:** `"Diary entry — {entry_date ISO} ({weekday English name})\nTitle: {title}\n\n"`,
     with the body `content`. An entry with empty content yields a single header-only chunk.
   - **Todo:** `"Todo: {title}\nStatus: {pending|completed}\nDue: {due_date ISO or 'none'}\nCreated: {created_at date ISO}\n\n"`,
     with the body `description`. No description yields a single header-only chunk.
   - The body is chunked with the existing `chunk_text(body, chunk_size - len(header), overlap)`.
   - If that budget drops below `chunk_size // 2` `(tune)`, the header's title is truncated with
     `…` until it fits. This guarantees `len(chunk) <= chunk_size` for every chunk.
   - The weekday stays English regardless of the user's locale, since the system prompt is
     English and the model maps it.
2. [ ] `web-api/app/worker.py` — `_process_job`'s `job.chunk` stage replaces its two inline
   `composed = ...` branches with `compose_chunks(...)`. `upsert_chunks` keeps receiving
   `source_date` (`entry_date` for diaries, `due_date or created_at.date()` for todos). It's
   still stored in the `date` payload for the prompt and references, but no longer used for
   scoring.
3. [ ] `web-api/app/vector_store.py` — `search()` drops `_recency_bonus`, `_hybrid_score`, the
   candidate pool and the `date.today()` re-sort. It returns `query_points(..., limit=top_k)`
   filtered to `user_id` as-is, ranked purely by cosine similarity.
4. [ ] `web-api/app/chat.py` — rewrite `build_system_prompt()`'s "prefer the latest [date]"
   rule. Each excerpt starts with its source's date and details, so for "latest / most recent /
   最近 / 最新 / 上次" questions the model compares the dates in the excerpts and answers from
   the newest relevant one. Add one line explaining the header format.

## 7. Backend: agent loop, chat memory, streaming, provider errors

Depends on Sections 2, 4, 5 and 6. Targets `web-api/app/chat.py` and
`POST /conversations/{id}/messages` in `web-api/app/routers/conversations.py`.

1. [ ] Chat memory (`chat.py`):
   - [ ] `rows_to_lc_messages(rows) -> list[BaseMessage]`, a 1:1 mapping:
     - `user` → `HumanMessage(content)`
     - `assistant` → `AIMessage(content, tool_calls=[{"id","name","args"}...])`
     - `tool` → `ToolMessage(content, tool_call_id, name=tool_name)`
   - [ ] `lc_messages_to_rows(messages, model_id) -> list[Message]` is the inverse, for the
     messages a turn produced:
     - Content is normalized with `_text_only(message.content)`, which keeps `type == "text"`
       blocks from list content, or the string as-is.
     - Reasoning/thinking blocks and `additional_kwargs["reasoning_content"]` are dropped.
     - Each provider tool-call id is rewritten to `call_<uuid4 hex[:24]>`, applied consistently
       to the AI message's `tool_calls` and the matching `ToolMessage.tool_call_id`.
   - [ ] `build_history_messages(db, conversation_id, before_seq) -> list[BaseMessage]`:
     - Finds the `CHAT_CONTEXT_TURNS`-th most recent `user` row before the current one and loads
       every row from it onward, ordered by `seq`.
     - Because the cut always lands on a human message, an AI tool call is never separated from
       its tool result.
     - `CHAT_CONTEXT_TURNS` keeps its meaning: user turns, not rows.
   - [ ] `build_turn_message(question, retrieved_chunks) -> HumanMessage`. The current-turn human
     message sent to the model is `"Retrieved excerpts:\n[date] chunk_text…\n\nUser's
     message:\n{question}"`, or the `_NO_CONTEXT_MARKER` text when nothing matched. Only the raw
     `question` is stored. This replaces `build_user_prompt()`, whose flattened
     "Recent conversation" text block is removed.
2. [ ] Agent run (`chat.py`):
   - [ ] `run_agent_stream(model_id, system_prompt, history, turn_message, tools) ->
     Iterator[AgentEvent]`:
     - Builds `create_agent(model=get_chat_model(model_id), tools=tools,
       system_prompt=system_prompt, middleware=[ModelCallSpanMiddleware(model_id)])`. The
       middleware comes from Section 9.
     - Calls `.stream({"messages": [*history, turn_message]}, stream_mode=["messages",
       "updates"], config={"recursion_limit": ...})`.
     - It yields `TokenEvent(text)` for every `AIMessageChunk` text block (after `_text_only`),
       and `ToolResultEvent(name, result)` after each tool node update.
     - At the end it yields `TurnCompleteEvent(new_messages)`, holding the AI/Tool messages
       produced after `turn_message`, taken from the final `updates`.
   - [ ] `GraphRecursionError`, raised when `CHAT_TOOL_MAX_ITERATIONS` is exhausted, is caught.
     The partial new messages are kept, and an `iteration_limit` error is yielded instead of
     crashing the stream. It is logged as a warning with provider/model, like today's
     `chat_tool_max_iterations reached`.
   - [ ] Delete `run_chat_with_tools`, `pending_action_reply`, `pending_action_is_confirmed`,
     `_CONFIRMATION_SCHEMA`, `_deterministic_failure_reply` and the `hard_failures` special
     case. Tool failures now just reach the model as tool messages (requirement 4).
3. [ ] `build_system_prompt()`:
   - Remove the wording that assumes a single flattened block, and the recency rule (rewritten in
     Section 4.4).
   - Keep: the date lookup table; "create_todo needs no confirmation"; "for
     update/complete/delete, ask first and only call with `user_confirmed=true` after the user
     agrees, never on your own judgment"; "if a tool result says needs_confirmation, ask the
     user"; "never claim a change you didn't make this turn"; the duplicate-title → due-date rule;
     the off-topic refusal; and reply-in-the-user's-language.
   - Add: "earlier turns in this conversation include the tools you actually called and their
     results — use them to know what you proposed and what already happened."
4. [ ] Provider error classification (`chat.py`):
   - [ ] `classify_provider_error(exc) -> str`, which inspects `status_code`/`response.status_code`
     and exception type names, so it doesn't hard-import every SDK:
     - 401/403 → `provider_auth`
     - 429 → `rate_limited`
     - `httpx.TimeoutException`, `*APITimeoutError` or `DeadlineExceeded` → `timeout`
     - anything else from a provider → `provider_error`
   - [ ] Provider errors are logged with `provider`, `model`, `error_type` and `status_code`
     only. That means `logger.warning(...)` without `exc_info`, because SDK exception messages
     can echo request bodies. Prompt text, diary content and keys are never logged. Non-provider
     bugs keep `logger.exception`.
5. [ ] `routers/conversations.py` `send_message`:
   - [ ] Resolve the effective model with `resolve_chat_model_id(conversation)`. If the model
     is cloud and `current_user.cloud_model_notice_acknowledged_at is None`, raise
     `HTTPException(409, detail={"code": "cloud_notice_required", "model": id})` **before**
     storing the user message, so a retry after acknowledging doesn't duplicate it.
   - [ ] Remove the `pending_action` branch entirely. The flow is: store the user row →
     `chat.embed_query` → `chat.qdrant_search` → `build_history_messages` → `chat.build_prompt`
     → `build_todo_tools(..., on_result=collect_mutation)` → `run_agent_stream`.
   - [ ] `event_generator()`:
     - It emits `references` (retrieval refs) first, then a `token` for each `TokenEvent`.
     - After each `ToolResultEvent` that mutated a todo, it emits a fresh `references` event
       with the full deduplicated list.
     - On `TurnCompleteEvent` it opens a new `SessionLocal()`, as today, and in one transaction:
       - inserts `lc_messages_to_rows(new_messages, model_id)` in order. `seq` comes from the
         identity column, so same-transaction ordering is preserved.
       - attaches `message_references` to the **final** assistant row
       - bumps `conversations.updated_at`
     - Then it emits `done` with the final row's `id`/`created_at`, plus `model`.
   - [ ] Exceptions raised while streaming become `{"event": "error", "data": {"message": ...,
     "code": classify_provider_error(exc)}}`. Whatever text streamed before the error is still
     not persisted, as today. The upfront `try` around retrieval maps to the same error event.
   - [ ] Tool mutations already committed by the tool handlers stay committed even if the
     stream later fails. That's the same as v0.5.0, and the todo itself is the source of truth.
