# Execution plan — v0.2.0

Ordered task breakdown for implementing v0.2.0, sequencing the work described in
[../architecture.md](../architecture.md#ai--rag-pipeline) against the acceptance criteria in
[../requirements/v0.2.0.md](../requirements/v0.2.0.md). This doc tracks *what to build and in what
order*, not design decisions — those live in architecture.md.

Confirmed decisions (see architecture.md for anything not called out here):
- **E2E testing**: the chat e2e spec runs against real Ollama + Qdrant, matching how v0.1.0's e2e
  already runs against real Postgres rather than mocks.
- **Conversation creation**: lazy — `POST /conversations` only fires on the user's first sent
  message; "New chat" is a client-only draft state until then.
- **Streaming transport**: `sse-starlette`'s `EventSourceResponse`, a new backend dependency.

Remaining implementation-detail parameters (chunk size/overlap, retrieval top-k, retry attempts,
exact embedding-model pull tag, etc.) are given reasonable defaults inline, flagged `(tune)` —
to be confirmed/adjusted during implementation rather than blocking this plan.

## 3. Backend indexing pipeline (worker + Qdrant)

Depends on Section 2. Must land before Section 5 (chat endpoint), since chat retrieval reads the
same Qdrant collection/payload shape the worker writes.

1. [x] `web-api/app/embeddings.py` — `embed_texts(texts, kind: Literal["query","passage"])`
   wrapping the Ollama embeddings API.
   - [x] Apply the `multilingual-e5-large` `"query: "`/`"passage: "` prefix convention.
     `(tune)` confirm whether the specific GGUF quant's Modelfile template already bakes this in
     (double-prefixing would be a bug). Applied unconditionally in code; not yet spot-checked
     against the live pulled model — flagged for the Section 10 acceptance walkthrough.
   - [x] Client factory is injectable/overridable, for the test doubles in Section 6.
2. [x] `web-api/app/vector_store.py` — Qdrant wrapper per
   [AI / RAG pipeline](../architecture.md#ai--rag-pipeline)'s vector-store spec.
   - [x] `ensure_collection()` — idempotent create of `diary_chunks` (vector size 1024, Cosine
     distance, payload index on `user_id`).
   - [x] `upsert_chunks(diary_entry_id, user_id, entry_date, chunks, vectors)` — delete-then-insert
     per entry, so edits re-embed cleanly.
   - [x] `delete_diary_entry_points(diary_entry_id, user_id)`.
   - [x] `search(user_id, query_vector, top_k)` — must treat a not-yet-existing `diary_chunks`
     collection as zero results rather than raising, so a chat request before any indexing has
     run doesn't 500. Only the worker calls `ensure_collection()` on startup; `web-api` doesn't
     force-create it at import time.
3. [x] `web-api/app/chunking.py` — pure function `chunk_text(content, chunk_size, overlap)`:
   paragraph-aware (split on blank lines), greedy packing, char-based overlap carryover,
   sentence-level fallback split for an oversized single paragraph. No I/O.
4. [x] `web-api/app/worker.py` — poll-loop entrypoint, invoked via the `worker` compose
   `command:` from Section 1.
   - [x] Startup: reset any `EmbeddingJob` rows stuck in `processing` back to `pending`
     (single-worker crash-recovery assumption — satisfies requirement 1's "resumable after
     restart"); call `ensure_collection()`.
   - [x] Loop body, implemented as a separately-testable function (not just the infinite loop):
     `SELECT ... FOR UPDATE SKIP LOCKED` on `status='pending'` ordered by `created_at` (FIFO, so
     rapid re-edits converge to the latest content); mark `processing` + commit; re-fetch the
     `DiaryEntry` (tolerate "entry no longer exists" — a delete race); chunk → `embed_texts(kind=
     "passage")` → `vector_store.upsert_chunks(...)` → mark `completed`.
   - [x] Failure path: on exception, increment `attempts`; requeue to `pending` if `attempts <
     embedding_job_max_attempts`, else mark `failed` with `error_message`.

## 4. Backend diary hooks

Wires the indexing pipeline into existing diary CRUD, per requirements 1 and 2.

1. [x] `web-api/app/routers/diaries.py` — `create_diary_entry`: after commit/refresh,
   `db.add(EmbeddingJob(diary_entry_id=entry.id)); db.commit()`.
2. [x] `update_diary_entry`: enqueue a new `EmbeddingJob` row only when `"content" in
   payload_fields` — re-index keys off content changes only (not title/date), matching the
   architecture doc's "splits the entry's markdown content" literally.
3. [x] `delete_diary_entry`: call `delete_diary_entry_points(entry.id, current_user.id)`
   **before** `db.delete(entry)`/`db.commit()` — opposite order from the existing media-file
   cleanup (which runs post-commit), because a Qdrant failure here must abort the whole delete
   rather than leave orphaned vectors; requirement 2 ("the chatbot can no longer reference it")
   is a correctness guarantee, not best-effort cleanup.

## 5. Backend RAG chat

Depends on Section 3 (shared `embeddings.py`/`vector_store.py`) and Section 2 (models/schemas).

1. [x] `web-api/app/chat.py`.
   - [x] `build_system_prompt()` — fixed scope-guarding instructions per
     [Scope guarding](../architecture.md#ai--rag-pipeline): answer only from retrieved diary
     context or Living-Genie app-help content; refuse everything else with a fixed rejection
     message regardless of phrasing (requirement 8); reply in the same language as the user's
     message (requirement 7), instructed via prompt rather than explicit language detection.
   - [x] `build_user_prompt(question, retrieved_chunks, recent_turns)` — when `retrieved_chunks`
     is empty, include an explicit "no relevant diary content found" marker so the model's "say
     so rather than fabricate" behavior (requirement 3) is unambiguous.
   - [x] `generate_reply_stream(system_prompt, user_prompt)` — streams from the Ollama chat model;
     injectable for tests. Reuses `embeddings.get_ollama_client()` (already
     `lru_cache`-based/overridable) rather than adding a second client factory.
2. [x] `web-api/app/routers/conversations.py` — `APIRouter(prefix="/conversations",
   tags=["conversations"])`.
   - [x] `_get_conversation_or_404(db, conversation_id, user_id)`, mirroring `diaries.py`'s
     `_get_entry_or_404` — this single helper satisfies requirements 4 and 6's "cross-user
     access/delete behaves like deleting/reopening a nonexistent conversation."
   - [x] `POST /conversations` — create an empty conversation, return `ConversationRead`. Per the
     confirmed lazy-creation decision, the frontend only calls this on the user's first sent
     message, not on "New chat" click.
   - [x] `GET /conversations` — `order_by(Conversation.updated_at.desc())`; each row's `preview`
     computed via a per-conversation lookup of the first `role="user"` message (requirement 5).
   - [x] `GET /conversations/{id}` — `_get_conversation_or_404`; eager-load messages ordered by
     `created_at`; enrich each assistant message's `cited_diary_entry_ids` into `CitationRead` via
     a live join against `DiaryEntry` (graceful fallback label if since-deleted).
   - [x] `DELETE /conversations/{id}` — `_get_conversation_or_404`; delete + commit; 204
     (requirement 6).
   - [x] `POST /conversations/{id}/messages` — the core RAG endpoint (requirement 3):
     1. [x] `_get_conversation_or_404`; validate `SendMessageRequest`.
     2. [x] Persist the user `Message` immediately, commit.
     3. [x] `embed_texts([content], kind="query")` → `vector_store.search(user_id filter, top_k)`.
     4. [x] Dedupe retrieved chunks into a citation list.
     5. [x] Fetch the last `chat_context_turns` messages for prompt context (requirement 4).
     6. [x] Build prompts via `app.chat`.
     7. [x] Return `sse_starlette.EventSourceResponse` whose generator yields, in order: a
        `citations` event (before generation starts, so the UI can show sources immediately),
        repeated `token` events (incremental text, accumulated server-side), then either a `done`
        event (new assistant message id/created_at, once persisted with `cited_diary_entry_ids`
        and `conversation.updated_at` bumped + committed) or an `error` event on failure (nothing
        persisted on error). Retrieval failures (steps 3–5) happen before the response is
        constructed, so they surface as a normal 500 rather than an SSE `error` event — only
        generation failures after streaming has started need the in-band event.
     8. [x] Ensure the generator's closing write (assistant message + `Conversation.updated_at`
        bump) doesn't depend on the request-scoped `Depends(get_db)` session outliving the
        response: opens a fresh `SessionLocal()` for that write instead, mirroring `worker.py`'s
        existing out-of-request session pattern, since FastAPI closes yield-dependencies before a
        streamed response finishes sending.
3. [x] `web-api/app/main.py` — `app.include_router(conversations.router)`.
