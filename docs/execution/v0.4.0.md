# Execution plan — v0.4.0

Ordered task breakdown for implementing v0.4.0, sequencing the work described in
[../architecture.md](../architecture.md) against the acceptance criteria in
[../requirements/v0.4.0.md](../requirements/v0.4.0.md). This doc tracks *what to build and in what
order*, not design decisions — those live in architecture.md.

Confirmed decisions (see architecture.md for anything not called out here):
- **One generic token table, not two**: `email_tokens` represents both a verification code and a
  reset code, discriminated by `purpose`, rather than two near-duplicate tables — the same
  generalization argument already applied to `embedding_jobs`'s `source_type`/`source_id`.
- **Code, not link**: verification/reset codes are delivered as a manually-entered code, never
  embedded in a URL, so an automated link-prefetching scanner can't burn a one-time token before
  the real user clicks it.
- **Silent no-op cooldowns**: re-requesting a verification/reset email within the cooldown window
  returns the exact same response as a successful send — this is load-bearing for the
  anti-enumeration guarantee, not just a rate limit, so it must never surface a distinct "please
  wait" response.
- **Auto-login on verify, not on reset**: `/auth/verify-email` issues a session and sets the
  cookie on success, exactly like `/auth/login` — no separate login step. `/auth/reset-password`
  deletes every other session for that user but does **not** create a new one; the resetting
  browser is redirected to `/login` to sign in with the new password.
- **Existing dev-DB accounts are grandfathered in as verified**: the migration backfills
  `email_verified_at = created_at` for rows that already exist, so accounts created before this
  version don't suddenly get locked out of login.

Remaining implementation-detail parameters (the exact shape of `UserRead`'s verification-status
field, `/auth/locale`'s response body, whether `email_tokens` needs a composite index) are given
reasonable defaults inline, flagged `(tune)` — to be confirmed/adjusted during implementation
rather than blocking this plan.

## 3. Backend: token helpers + email module

Depends on Section 2 (the `EmailToken` model must exist).

1. [x] `web-api/app/security.py` additions, parallel to the existing `create_session()`/
   `delete_session()` pair:
   - [x] `create_email_token(db, user_id, purpose) -> tuple[EmailToken, str]` — generates an
     `settings.email_code_length`-character code from an alphabet excluding visually ambiguous
     characters (`0`/`O`, `1`/`I`/`L`), hashes it with `hashlib.sha256` for `code_hash`, sets
     `expires_at` based on `purpose` (`email_verification_token_expire_minutes` vs.
     `password_reset_token_expire_minutes`), persists the row, and returns `(row, plaintext_code)`
     — the plaintext is never stored, only returned once for the caller to email.
   - [x] `invalidate_email_tokens(db, user_id, purpose) -> None` — deletes any existing outstanding
     row(s) for that `user_id`/`purpose` pair.
   - [x] `consume_email_token(db, user_id, purpose, code) -> EmailToken | None` — looks up the
     outstanding row for `user_id`/`purpose`; if missing or expired, returns `None`; otherwise
     compares the submitted code's hash via `hmac.compare_digest`. A match deletes the row (single-
     use, mirroring `delete_session()`) and returns it; a mismatch increments `attempts` and, once
     it reaches `settings.email_code_max_attempts`, deletes the row (same effect as expiry) —
     either way returns `None` for a mismatch.
2. [x] `web-api/app/email.py` (new, flat layout matching `embeddings.py`/`chunking.py`):
   - [x] `_EMAIL_COPY = {"en": {...}, "zh-Hant": {...}}` — subject/body strings for both emails in
     both locales; inline dict, not a general i18n framework, matching the frontend's own
     small-eagerly-loaded-JSON reasoning.
   - [x] `async def send_verification_email(user: User, code: str) -> None` and
     `async def send_password_reset_email(user: User, code: str) -> None` — select copy via
     `user.locale`, build a multipart (plain-text + HTML) message via
     `email.message.EmailMessage`, send via `aiosmtplib.send(...)` using the `smtp_*` settings
     (`.login()` skipped entirely when `smtp_user` is empty). Body shows the plaintext code
     prominently plus its validity window; may include a plain convenience link to the app's
     verify/reset page, but never embeds the code itself in a URL. Both functions catch and log any
     exception rather than raising — best-effort, since callers must still succeed even if SMTP is
     briefly down.
   - [x] Both are `async def` specifically so they can be passed directly to FastAPI's
     `BackgroundTasks.add_task(...)` and awaited natively by `aiosmtplib`, without a thread-pool
     hop.

## 4. Backend: auth endpoints

Depends on Sections 2-3. Extends the existing `web-api/app/routers/auth.py`
(`APIRouter(prefix="/auth", tags=["auth"])`) in place — no new router module.

1. [x] `POST /auth/register` — accept `UserCreate.locale`, persist it on the new `User` row; after
   commit, `create_email_token(purpose="email_verification")`, set
   `last_verification_email_sent_at = now()`, and schedule
   `background_tasks.add_task(send_verification_email, user, code)`. Response shape/status (`201` +
   `UserRead`) unchanged; the account is created exactly as today, just unverified.
2. [x] `POST /auth/login` — after password verification succeeds, check
   `user.email_verified_at is None`; if so, raise `HTTPException(403, ...)` with a message
   distinct from the generic incorrect-credentials text, *before* creating a session. A wrong
   password on any account (verified or not) still raises the existing generic `401` unchanged.
3. [x] `POST /auth/resend-verification` (`ResendVerificationRequest` in, `202` always out,
   identical body regardless of outcome):
   - [x] Look up the user by email; if not found, or already verified, or within
     `resend_verification_cooldown_seconds` of `last_verification_email_sent_at`: no-op, return the
     same `202`.
   - [x] Otherwise: `invalidate_email_tokens(purpose="email_verification")`,
     `create_email_token(...)`, update `last_verification_email_sent_at`,
     `background_tasks.add_task(send_verification_email, ...)`, return the same `202`.
4. [x] `POST /auth/verify-email` (`VerifyEmailRequest` in):
   - [x] Look up the user by email; if not found, `consume_email_token(purpose="email_verification")`
     against a nonexistent user id can't succeed, so this naturally falls into the same generic
     failure path as an expired/wrong code — no distinguishable response. `(tune)` resolved: rather
     than actually calling `consume_email_token` with a fabricated id, the lookup is simply skipped
     when the user isn't found and control falls straight through to the shared failure branch —
     same observable `400`, no invented sentinel id.
   - [x] On a successful `consume_email_token(...)`: set `email_verified_at = now()`,
     `create_session(...)`, set the session cookie (same `httponly`/`samesite`/`secure` flags as
     `/auth/login`), return `200` + `UserRead`.
   - [x] On failure (`None` returned, or user not found): `400` with a single generic "invalid or
     expired code" message — covers wrong code, expired code, already-used code, and
     already-locked-out code identically, per requirement 3's acceptance criteria.
5. [x] `POST /auth/forgot-password` (`ForgotPasswordRequest` in, `202` always out) — same shape as
   item 3 above but for `purpose="password_reset"`, `last_password_reset_email_sent_at`, and
   `send_password_reset_email`; no "already verified" no-op case (unlike resend-verification, an
   unverified account can still request a password reset).
6. [x] `POST /auth/reset-password` (`ResetPasswordRequest` in):
   - [x] Same lookup-and-consume pattern as `verify-email` but for `purpose="password_reset"`.
   - [x] On success: `hash_password(new_password)` → `user.hashed_password`; delete every existing
     `sessions` row for that `user_id` (all of them — there's no "current" session yet, since this
     request isn't authenticated); `create_session(...)` for the new session and set the cookie;
     return `200` + `UserRead`.
   - [x] On failure: same generic `400` "invalid or expired code" message as `verify-email`.
7. [x] `PUT /auth/locale` (`LocaleUpdate` in, requires `Depends(get_current_user)`) — updates
   `current_user.locale`, commits, returns `200` + `UserRead`. `(tune)` resolved as `200`+`UserRead`
   — more useful to the frontend since it can refresh the cached user without a separate
   `/auth/me` round trip.
8. [x] `web-api/app/main.py` — no change needed; `auth.router` is already registered and these are
   all new routes on the existing router object.

Implementation note: two small private helpers were added to `auth.py` to avoid duplication —
`_in_cooldown(last_sent_at, cooldown_seconds)` (shared by items 3 and 5) and
`_set_session_cookie(response, session)` (shared by `/auth/login`, `/auth/verify-email`, and
`/auth/reset-password`, which now all set the cookie identically). All endpoints stayed sync
`def` (matching every other router in the codebase, which uses the sync SQLAlchemy `Session`);
the async `send_verification_email`/`send_password_reset_email` are scheduled via
`background_tasks.add_task(...)`, which Starlette runs natively for async callables. Known
follow-on effect, left for Section 5: the shared `register_and_login` test helper in
`tests/conftest.py` now fails, since login 403s until the account is verified — this breaks the
wider test suite (87 errors) until Section 5 updates that fixture and adds `fake_email_sender`.
